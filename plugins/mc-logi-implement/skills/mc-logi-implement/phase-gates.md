# phase-gates.md — phase 별 산출물·게이트·재개 규약

## 산출물·게이트 표

| Phase | 산출물 (재개 판정 기준) | 게이트 | 게이트에서 묻는 것 |
|---|---|---|---|
| 0 키트 | 키트 디렉터리 + version-master 신선 | (자동) | CHANGED 다수 시에만 영향 확인 |
| 1 스펙 | `docs/superpowers/specs/YYYY-MM-DD-{slug}-design.md` (커밋) | **게이트 1** | 스펙 검토·승인 (수정 요청 루프) |
| 2 플랜 | `docs/superpowers/plans/YYYY-MM-DD-{slug}.md` (커밋) | **게이트 2** | 플랜 승인 + 실행 방식 (서브에이전트 권장/인라인) |
| 3 구현 | `feature/{slug}` 브랜치 — 태스크별 커밋 + 최종 리뷰 통과 | (자동) | BLOCKED/정책 차이 발견 시에만 |
| 4 반영 | 클린 테스트·빌드 그린 (+지시 시 DB 적용 검증) | **게이트 3** | 머지 방식 (main 머지/브랜치 유지/PR) |
| 5 추적 | IMPREC N건 + 키트 IMPLEMENTATION.md 갱신 커밋 | (종료) | mc-logi-update 권고 제시 + 메모리 저장 문의 |

## 재개 (phase 인자)

사용자가 재개 지점을 말하면 ("플랜부터", "구현 이어서", "추적만"):

1. 해당 phase 의 **선행 산출물 존재**를 위 표로 검증 — 스펙 없이 플랜 불가, 플랜 없이 구현 불가.
2. 선행 산출물이 있으면 그것을 읽어 컨텍스트 복원 (스펙의 결정 사항·플랜의 태스크 체크박스 상태).
3. 구현 재개는 플랜의 체크박스(- [ ]/- [x])와 git log 로 완료 태스크를 식별해 다음 태스크부터.
4. Phase 0 (키트 게이트)은 **재개 시에도 생략하지 않는다** — 키트 신선도가 모든 phase 의 전제.

## 게이트 운영 원칙

- 게이트는 **사용자 결정이 필요한 지점**이다 — 승인 요청을 진행 보고와 분리해 명확히 묻는다
  (AskUserQuestion 또는 명시적 질문). 게이트 사이에서는 "계속할까요?" 류 중간 확인을 하지 않는다.
- 게이트 밖 추가 질문이 허용되는 경우: 구현 중 발견된 **정책 차이**(키트 ⚠️ 에 답이 없고
  레포 동작을 바꾸는 결정), 파괴적 작업(DB 적용·운영 데이터), 범위 변경.
- 사용자가 게이트에서 방향을 바꾸면 (범위 축소·접근 변경) 해당 phase 산출물을 수정 커밋하고
  이후 phase 산출물은 무효 처리(재생성).

## 보고 포맷 (phase 전환 시)

각 phase 종료 시 한 단락 요약 + 다음 게이트 질문. 최종(Phase 5) 보고는:

```markdown
# {DOMAIN-ID} {도메인명} 구현 완료

## 결과
- 브랜치/머지: ... / 테스트: N건 그린 / 커밋: N건
- 구현 영역: (키트 영역 표 기준 — 완료/부분(잔여 명시)/제외)

## logicraft 추적
- IMPREC: ... (implemented N / in_progress N)
- 도메인 커버리지: code N건 avg N%

## 구현 중 확정 사항 (→ mc-logi-update 권고)
- (설계 ↔ 현실 차이와 채택한 결정, 키트/스펙 근거)

## 운영 전 확인
- (키트가 수동 절차·spec-pending 으로 표기한 잔여 사항)
```

## 이 스킬이 하지 않는 것

- logicraft 설계 ITEM 의 data 수정 (→ mc-logi-update)
- 키트 생성·동기화 자체 (→ mc-logi-implement-kit 호출로 위임)
- 도메인 갭 검출 (→ mc-logi-domain-review)
- 키트 없이 "기억"으로 구현 — 키트가 없고 만들 수도 없으면 중단이 맞다
