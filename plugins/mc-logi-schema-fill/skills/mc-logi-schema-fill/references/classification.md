# 분류 기준 — 이 참조는 «칸에 올릴 관계»인가

`scan_prose_refs` 가 보여 주는 건 **「산문에 ID 가 있는데 그 칸이 비어 있다」** 뿐이다.
그 ID 가 **정말 이 항목이 기대는 대상인지**는 판별기가 모른다. 그걸 가르는 게 이 단계다.

## 왜 이게 중요한가

칸에 올리면 **링크(엣지)**가 생긴다. 링크는 cascade 의 길이다 — 대상이 바뀔 때마다 이 항목에
「재검토 필요」가 붙고, `analyze_impact` 가 이 항목을 영향 범위에 넣는다.
**관계가 아닌 것을 올리면 틀린 엣지가 영구히 남아** 엉뚱한 곳에 재검토 표시를 뿌린다.
반대로 진짜 관계를 빼면 cascade 가 그 항목을 못 본다(그게 이 이관을 하는 이유다).

실측(LogiCraft Self, 2026-09): 발화 167건 중 **28건(17%)이 올리면 안 되는 것**이었다.
감으로 전부 올리면 여섯 건 중 한 건이 틀린 엣지가 된다.

## 판정 순서

1. 그 ID 가 **어느 문장에** 있는지 읽는다 — `locations` 가 가리키는 경로를 `get_item` 으로 본다.
   ☠️ ID 만 보고 판정하지 마라. 같은 ID 도 문장에 따라 관계일 수도, 예시일 수도 있다.
2. 아래 **제외 부류**에 해당하는지 본다. 하나라도 맞으면 그 부류로.
3. 해당이 없고 「이 항목이 그 대상을 **전제·구현·준수·사용**한다」가 문장에서 읽히면 **이관**.
4. 어느 쪽인지 문장만으로 확신이 안 서면 **보류**. 보류는 실패가 아니다 — 사람이 볼 목록이다.
5. 행에 **🚧 `guard`** 가 붙어 있으면(같은 문장의 경계·선례 문구, 또는 「잔여」「해소되지 않은 것」「책임 제외」 같은
   **절 제목** 아래) 기본값은 **경계 선언·선례 인용·보류** 쪽이다. 그래도 이관이면 «왜 관계인지»를 `reason` 에 쓴다 —
   안 쓰면 스크립트가 거부한다. 실측: 3-모델 교차 판정에서 틀린 이관 4건이 전부 이 자리였다(IMPREC 의 「## 잔여」,
   「범위가 아니므로 손대지 않았다」, 「(ADR-099 패턴)」, DOMAIN 의 「책임 제외」 절).

## 부류

### 이관 — 진짜 관계
이 항목이 그 대상에 **기대고 있다**. 대상이 바뀌면 이 항목도 다시 봐야 한다.
- 「이 API 는 ADR-025 의 봉인 원칙을 따른다」 → `based_on_adrs` 에 ADR-025
- 「FEAT-048 의 business_rules 를 구현한다」 → `implements_features` 에 FEAT-048
- 판단 질문: **「그 대상이 내일 바뀌면, 이 항목을 다시 열어 봐야 하나?」** — 예면 이관.

### 다른 항목의 사례 (예시)
설명 속에 **예로 든** 번호. 그 항목을 참조하는 게 아니다.
- 「예를 들어 FEAT-001 의 implements_requirements 에 REQ-005 가 적혀 있으면…」 → REQ-005 는 예시
- 「`#API-004` 와 `API-004` 가 같게 동작한다」(검색 토큰화 설명) → API-004 는 예시
- 샘플 데이터·예시값(`sources: [ERD-001]` 같은 예시 JSON)
- 신호: 「예:」「예를 들어」「가령」「~처럼 적혀 있으면」, 백틱 안의 형식 설명

### 선례·비유 인용
**비교 대상**으로 든 번호. 「A 와 같은 방식으로」라고 말해도 A 에 기대는 건 아니다.
- 「ADR-004 에서 겪은 것과 같은 함정」 → 선례
- 신호: 「~처럼」「~와 같은 방식」「~때와 마찬가지로」「선례」

### 경계 선언
**연결하지 «않았다»**, 또는 **범위 밖**이라는 선언. 올리면 정반대 뜻이 된다.
- 「Phase 3 enum 변형(DFEAT-043)은 **별도**」 → 경계
- 「ROLE-005 RBAC **미연결** → 향후 교체」 → 연결 안 했다는 뜻
- 「본 UC **범위 외**」「~와 **무관**」「~는 다루지 않는다」
- ☠️ 가장 위험한 부류다 — 올리면 「따른다」가 된다. 부정어를 반드시 확인하라.

### 쓰지 않게 된 이력
**예전에는** 그랬다는 기록. 지금은 아니다.
- 「원래 ADR-012 방식이었으나 CO-100 에서 제거」 → 이력
- 신호: 「예전에는」「원래」「~였으나」「대체됨」「폐기 전에는」

### 폐기 항목
**이 항목(주체) 자체가 폐기**됐다. 폐기된 것에서 새 엣지를 만들지 않는다.
- 스캔 행의 `item_status` 가 `deprecated`·`superseded` 면 **기계적으로** 이 부류다(도우미가 자동으로 채운다).

### 측정 표본
그 항목을 **측정·실험의 재료**로 썼을 뿐이다.
- 「무손실 실측: ADR-025 61리프 / DFEAT-056 29리프 누락 0」 → DFEAT-056 은 표본
  (이 모듈이 실제로 realize 하는 건 다른 항목이다)
- 신호: 「실측」「표본」「샘플로」「~로 검증했다」 + 숫자

### 목업 라벨
와이어프레임·목업·렌더 **안에 그려 넣은 글자**.
- `static_renders[…].components[…].label` 에 적힌 ID
- 신호: `locations` 경로가 `static_renders`·`design_renders`·`wireframe`·`mockup`·`components[].label` 안

### 형제 프로젝트 번호
**다른 프로젝트**의 결정 번호. 이 프로젝트에 같은 번호가 있어도 **다른 것**이다.
- 「형제 프로젝트 ADR-037 — 별도 프로젝트라 link 불가」 → 이 프로젝트의 ADR-037 과 무관
- ☠️ 올리면 **조용한 오엣지**가 된다 — 번호가 실재하니 에러도 안 난다.
- 신호: 「형제」「다른 프로젝트」「○○ 프로젝트의」「별도 레포」

### 범위 표기가 «기간»을 뜻할 때 (보류·제외)
「ADR-105~115 **시기에는**」처럼 범위가 **두 결정 사이의 기간**을 말하면, 판별기가 펼친 중간 번호(ADR-106~114)는 **참조가 아니다**.
원문에 그 번호가 글자로 없다 — 문맥을 확인하면 드러난다(KLID 2차 API-329 실측). 범위가 «이 목록 전부»(「API-279~284 엔드포인트」)를 뜻할 때만 이관 후보다.

### 보류
문장만으로 판정할 수 없다. **사람이 본다.**
- 「정렬한 곳은 FEAT-048 business_rules 다」 — 자기가 구현한다는 말인지, 다른 곳을 가리키는지 모호
- 같은 클러스터라 실제 관계일 가능성이 남는 경우

## 흔한 실수

| 실수 | 결과 |
|---|---|
| ID 만 보고 판정 | 경계 선언·예시를 이관으로 — 틀린 엣지 |
| 「같은 도메인이니 관계일 것」 | 추정으로 올림 — 문장이 말하지 않으면 보류 |
| 부정어를 놓침(「별도」「미연결」「범위 외」) | 정반대 뜻의 엣지 |
| 모든 발화를 이관 | 17% 가 틀린 엣지 |
| 애매한 걸 억지로 한쪽에 | 보류로 두는 게 맞다 — 보류는 실패가 아니다 |

## 사유 적는 법

제외·보류는 **반드시 사유를 한 줄** 적는다 — 그 문장의 핵심 구절을 인용하라.
사유가 없으면 나중에 누가 「왜 안 올렸지?」 하고 올려 버린다. 사유가 곧 방어선이다.

좋은 사유: `「Phase 3 enum 변형(DFEAT-043)은 별도」 — 연결하지 않았다는 선언`
나쁜 사유: `관계 아님`
