# 재료 D — 코드 근거로 «구현 사실» 칸 채우기

## 왜 코드인가

새 연결 칸에는 두 종류가 있다.

| 종류 | 예 | 진실원 |
|---|---|---|
| **구현 사실** | API 가 어느 테이블을 읽고 쓰나(`operates_on`) · 어느 권한을 요구하나(`required_roles`) | **코드**. 산문은 낡을 수 있지만 코드는 지금 도는 모습이다 |
| **설계 의도** | 어느 결정을 따르나(`based_on_adrs`) · 어느 요구를 구현하나(`implements_requirements`) | 코드에 없다 — 산문(재료 C)·사람 |

산문에 ID 가 없는 항목(상용 Self 실측: 연결 칸이 전부 빈 항목 1,218/1,524)은 산문 이관으로는 영영 안 채워진다.
코드가 있는 프로젝트라면 구현 사실 칸은 **코드를 먼저** 본다.

대상 칸(`scripts/schema_fill.py` 의 `CODE_FACT_FIELDS`):

| 타입 | 칸 | 코드에서 무엇을 보나 |
|---|---|---|
| api_endpoint | `operates_on` (ERD) | 그 핸들러가 **실제로 읽고 쓰는 테이블** — 컨트롤러 → 서비스 → 쿼리(ORM 테이블 심볼·SQL) |
| api_endpoint | `required_roles` (ROLE) | 그 라우트의 **권한 가드** — 데코레이터·미들웨어·가드 함수가 요구하는 역할/권한 코드 |
| service_interface | `operates_on` (ERD) | 그 도구·핸들러가 읽고 쓰는 테이블 |
| domain_feature | `operates_on` (ERD) | 그 기능의 모듈들이 영속하는 테이블 |
| domain_feature | `required_roles` (ROLE) | 그 기능 진입점들이 요구하는 역할 |
| code_module | `follows_guidelines` (GUIDE) | 그 파일 코드가 가이드라인 규칙을 **실제로 구현**하는가(예: GUIDE-001 응답 런타임 가드 → `Array.isArray`·요소 필터 줄). 규칙 대상인데 구현이 없으면 「안내」(가이드라인 위반 가능) · 적용 범위 밖(서버 코드·순수 UI)은 「해당 없음」 |

## 판정 전에 — 레포가 최신인가
☠️ 로컬 체크아웃이 원격보다 뒤처져 있으면 설계가 가리키는 파일·줄이 없다(NexusSystem 실측: 로컬 main 이 origin 보다 약 130커밋 뒤 — `MyRoleController` 등 부재).
`git -C <레포> fetch && git -C <레포> rev-list --count HEAD..@{u}` 가 0 이 아니면 **작업 트리를 건드리지 말고** 최신 커밋을 별도 워크트리로 받아
(`git worktree add --detach <임시경로> origin/main`) 그 경로를 작업표 `repo_root` 로 판정한다(근거 줄 번호가 그 커밋 기준이 된다 — 작업표에 커밋을 적어 둔다).

## 역할 칸(`required_roles`) — 권한 코드와 역할 항목이 어긋날 때
코드는 흔히 역할이 아니라 **권한 코드**(`hasAuthority('employee:read')`)를 검사한다. 두 집합을 비교해 **일치할 때만** 채운다:
① 코드 시드(마이그레이션·seed)에서 그 권한을 가진 역할 ② ROLE 항목 data 의 permissions 가 그 API 의 기능·동작을 덮는 역할. 다르면 보류(차이를 사유에).
소유자 조건(`isOwner`)·서비스 계정·클라이언트 스코프는 역할이 아니다 — 보류. 로그인만 확인 → 해당 없음.
☠️ **코드가 역할을 «직접» 쓸 때만 채움** — 권한이 DB 매트릭스·메뉴코드로 정해지거나(KLID `decodeHeaderToken(request,"NN")`),
`canWriteX()` 같은 로직에서 역할을 추론해야 하면 **보류**(사유에 추론 경로). KLID 상용: 로직에서 추론한 역할 19줄을 사용자가 기각했다.
LogiCraft Self 상용: 「코드 확인」으로 채운 `[ROLE-001~003]` 이 코드 역할 시드(PM·PL·기획자…)와 1:1 이 아니었다.

## 판정 절차 (행마다)

1. **코드 위치 찾기** — `code_hints`(method·path·module_paths·title)로 진입점을 찾는다. API 는 `method`+`path` 로 라우트 선언을 grep, SVC 는 도구 이름.
2. **호출을 따라간다** — 진입점 → 서비스 → 저장소/쿼리. 한 홉에서 멈추지 마라(컨트롤러는 테이블을 안 부른다).
3. **ID 로 옮긴다** — 찾은 테이블 이름을 그 테이블을 담은 ERD 항목(물리 테이블 목록)으로, 가드의 역할/권한 코드를 ROLE 항목으로. `list_items(type=erd)`·`get_item` 으로 **실재하는 ID** 만.
4. **근거를 적는다** — `basis`: `코드: <레포 상대경로>:<줄> — <그 줄 근처의 글자 그대로 조각>`. 근거가 여럿이면 ` … ` 로 잇는다
   (예: `코드: apps/api/src/modules/design-presets/design-presets.service.ts:88 — from(designPreset) … 코드: apps/api/src/modules/design-presets/design-presets.controller.ts:31 — @Get()`).
   스크립트가 파일·줄이 실재하고 **그 줄 ±3 안에 조각이 글자 그대로** 있는지 검사한다 — 지어낸 경로·심볼은 거부된다.
5. **판정**

| verdict | 언제 |
|---|---|
| 채움 | 코드에서 확인했다 — `value`(ID 배열) + `basis`(코드 근거) |
| 해당 없음 | 코드상 테이블을 안 건드린다(순수 계산·외부 호출만) / 가드가 없다(공개 라우트) — `reason` 에 코드 근거 |
| 안내 | 코드를 못 찾았다(미구현·레포 밖) — `reason` |
| 보류 | 테이블↔ERD 대응이 애매하다(한 테이블이 여러 ERD 에 걸침 등) |

## 함정

- ☠️ **산문과 코드가 다르면 코드를 따르고, `note` 에 「산문 불일치」 를 적는다** — 설계가 낡은 곳을 찾는 부수 효과다. 검토표에서 따로 보여 준다.
- ☠️ **읽기 전용 조회도 `operates_on` 이다** — 쓰기만이 아니다(칸 설명: 「관련 데이터 모델」).
- ☠️ **감사 로그·이벤트 아웃박스처럼 모든 쓰기가 공통으로 남기는 테이블은 넣지 마라** — 모든 API 가 같은 ERD 를 가리키면 그 ERD 가 바뀔 때 전부 재검토가 뜬다(소음). 그 기능의 본 테이블만.
- ☠️ **인증 세션 확인(로그인 여부)만 하는 가드는 역할이 아니다** — `required_roles` 는 특정 역할·권한 코드를 요구할 때만.
- 코드 근거로 채운 값은 **산문 복사가 아니다** — 서버는 새 관계로 보고 하위 항목에 재검토 표시를 붙인다. 실제로 새 관계가 생긴 것이라 정상이다. 적용은 `apply --probe` 로 하되, 이 라운드는 **하위 표시가 생기는 게 예상 동작**이다 — 멈추면 목록을 보고 «예상한 하위인가»만 확인하고 `--only` 로 이어 간다.
