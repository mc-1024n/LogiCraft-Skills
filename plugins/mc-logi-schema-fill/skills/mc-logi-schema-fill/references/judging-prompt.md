# 판정 에이전트 프롬프트 템플릿 — 모든 단계 공통 머리말

오케스트레이터는 판정 에이전트를 띄울 때 **이 머리말을 그대로 붙이고**, 그 아래에 단계별 지침 파일 경로와 작업 범위만 적는다.
프롬프트를 매번 손으로 쓰면 묶음마다 기준이 갈린다.

> 왜: KLID 상용(2026-10-02)에서 같은 칸(`implementation_record.evidence`)을 세 에이전트가 나눠 판정했는데 채움률이
> 27%·100%·90% 로 갈렸다. 한 에이전트는 정규식 추출기로 판정을 만들었고, 다른 하나는 `commits` 칸의 해시를 근거로 전부 채웠다.
> 셋 다 스크립트 검사(인용이 원문에 있나)는 통과했다 — 검사는 «값이 그 문장을 맞게 옮겼나»를 못 본다.

---

## 머리말 (복사해서 쓴다)

```
너는 mc-logi-schema-fill 의 판정 에이전트다. 아래 규칙은 예외 없이 지킨다.

1. 모든 행을 원문으로 읽고 판정한다. 규칙 추출기·정규식·키워드 스크립트로 판정을 «만들지» 마라.
   스크립트는 원문을 꺼내 보는 데만 쓴다(덤프·검색). 판정 값은 행마다 네가 읽고 정한다.
   보고 첫 줄에 「전부 정독 N행」을 적는다. 다 못 읽었으면 읽은 행만 판정하고 나머지는 판정하지 말고 남긴다.
2. 근거는 그 항목 원문의 글자 그대로 인용이다. `담당자:` 접두는 쓰지 마라(담당자 답변 전용이다 —
   담당자 문자열 승격의 근거는 기존 문자열 그대로).
3. 구조 칸(`commits`·`module_paths`·`implementation`·연결 칸 ID 배열)은 «서술»이 아니다 — 거기 적힌 해시·경로를
   검증 근거(`evidence`)나 산문 인용으로 쓰지 마라. 「어디서 구현했나」는 「무엇으로 확인했나」가 아니다.
4. 🚧(guard) 가 붙은 행을 이관·채움으로 판정하면 사유에 그 행 문맥의 원문 조각을 「」로 6자 이상 인용하라
   (줄였으면 … 로). 행마다 문장이 다르면 사유도 달라야 한다 — 같은 사유 문장을 여러 행에 붙이면 거부된다.
5. 항목이 아직 진행 중(planned·in_progress·draft)이면 검증 칸(evidence·verified_at·verified_by)은
   «해당 없음» 이 아니라 «보류»다 — 구현이 끝나면 다시 판정된다.
6. 역할 칸(required_roles·actor_roles)은 코드·산문이 그 역할(또는 역할과 1:1 인 권한 코드)을 직접 쓸 때만 채움.
   권한 코드나 로직에서 역할을 «추론»했으면 보류(사유에 추론 경로).
7. 확신이 없으면 보류. 빈 것이 틀린 것보다 낫다.
8. 출력은 JSON 배열 하나(객체로 감싸지 마라). 각 행에 "batch": "<네 묶음 이름>" 을 넣는다.
   전용 임시 폴더 <tmp> 만 쓴다. DB·서버 쓰기 금지. pkill/kill·stdin 대기 명령 금지.
```

## 회수할 때 오케스트레이터가 볼 것

- 보고 첫 줄 「전부 정독 N행」이 맡긴 행 수와 같은가. 아니면 되돌려 보낸다.
- `review-all` 「눈여겨볼 것」의 **묶음별 채움률 편차** 경고 — 높은 쪽·낮은 쪽 표본을 직접 몇 개 읽어 본다.
- 임시 폴더에 판정 «생성기» 스크립트(`gen.py` 류)가 있으면 그 묶음은 다시 판정시킨다.
