# Phase 5 검증 — 왜 이 검사들이 있나 (배경과 실측)

> SKILL.md Phase 5 의 검사 목록은 짧게 «무엇을 보나»만 적는다. 여기는 «왜»다 — 검사를 빼고 싶어질 때 먼저 읽는다.
> 사례 이름은 익명이다(실측 사례 A~E — 특정 조직·프로젝트를 가리키지 않는다).

## 받은 값이 방출물에 «실렸는지» — QA 4값 · backfill_model

- 2026-09-16 에 QA 모델 인터뷰만 추가되고 **dispatch 템플릿에 슬롯이 없어** 받은 답이 어디에도 안 실렸다(2026-09-18 발각).
  물어만 보고 흘리면 안 한 것과 같다 — 다음 세션은 그 값을 모른다.
- 2026-09-19 까지 이 검사에는 **QA 4값만** 있었다. 백필 워커 모델은 인터뷰에서 받고 템플릿에도 슬롯이 있었는데
  **실렸는지는 아무도 안 봤다** — 같은 사고가 그대로 재현될 자리였다.
- 1.9.0 까지 Phase 5 는 QA 4값이 **build 에도** 실렸는지 봤는데 build 템플릿에는 그 슬롯이 0개였다 —
  `has_build=on`(기본 P1)이면 이 검사가 늘 실패했다. 1.10.0 에서 build Phase E 에 표를 넣었다.
- ★ 비워 두기로 한 값은 빈 문자열을 grep 하면 언제나 통과한다 — 그건 검사가 아니다.
  그래서 비운 `backfill_model` 은 **「비움 = `<qa_model>` 과 동일」 문장**이 실렸는지로 본다(템플릿이 슬롯 조건으로 그 문장을 낸다).

## 노하우 색인·상시·knowhow_read — 세 역할 전부

- QA 템플릿에는 2026-09-19 전까지 색인 절이 **아예 없었다** — 노하우를 가장 많이 쓰는 역할인데.
- 재온보딩 직후 QA 본체가 색인만 남자 QA 두 판 모두 묶음 열람 0건이었고, QA 가 알던 함정(병렬 중 `git stash`)을
  그 라운드에 다시 밟았다(실측 사례 C).

## 머리말 규칙이 «재어지는지» — limit=40 · how · 대조 스크립트의 "limit"

- 지침만 있고 검사가 없으면 3라운드 안에 무너진다(권유형 색인 전례).
- 전사본에 offset·limit 이 **이미 들어 있는데** 옛 대조 스크립트는 `file_path` 만 뽑아 버렸다.
  데이터가 있는데 **측정기가 안 보고 있었다** — 그래서 「머리말만 읽었나」는 한 번도 검사된 적이 없었다.
- ⚠️ 전사본 형식은 Claude Code 내부 형식이다 — 버전이 바뀌면 경로·필드가 달라질 수 있다. 0건이면 「측정 불가」로 보고한다.

## 머리말 생성기 — 파생물

- 실측(사례 C): 묶음 분리로 본체를 3,333→708줄로 줄였는데 **전문 열람 탓에 노하우 주입이 2.7배로 늘었다.**
  머리말 도입 후 A/B 에서 **주입 −93% · 소요 −80%**, 판정 품질 저하 신호 없음.
- 항목을 더하면 줄 번호가 밀려 「여기로 가라」가 엉뚱한 곳을 가리킨다(끊긴 참조와 같은 유형). 그래서
  Phase 5.9(노하우 append) 절에 재생성 호출이 있어야 하고, 최종 검증에서 `--check` rc=0 을 본다.
- 1.9.0 까지는 삽입이 줄 번호를 미는 탓에 **두 번 돌려야** 고정점에 갔다(1회 뒤 `--check` 가 rc=1).
  1.10.0 부터 생성기가 **스스로 고정점까지 반복**한다 — 한 번 돌리고 rc=0 이 아니면 그것이 진짜 이상이다.
- 생성기의 `re.sub` 치환은 `lambda` 로 막아 두었다 — 문자열로 주면 본문의 `\x`·`\1` 이 치환 이스케이프로 터진다
  (첫 실행은 그 분기를 안 타서 재실행 때만 드러났다). 고치지 마라.

## 작성 규칙(1.6.0) — 설계는 «처음부터 칸에»

- 하나라도 빠진 세트는 설계에 관계를 산문으로 쌓는다 — 옛 산문을 칸으로 옮겨 두어도 **다시 쌓인다.**
- backfill 의 「단계마다 «성공 판정»」 표: 초안 단계가 verdict 부재로 exit 20 오판을 낸 실측(2026-10-01)에서 나왔다.
- 「재검토 표시 보존 검사」: 백필 저장 8항목에서 자동 재검토 표시 58건이 사라진 실측(2026-10-01)에서 나왔다.

## 끊긴 참조 검사

- 실측(사례 C 2차 재온보딩) — 묶음을 600줄 상한으로 **쪼개면서 본체의 참조를 안 고쳤다.**
  하필 **가장 강한 읽기 지시**(「관계 축 작업 전 **반드시** 열어 읽을 것」)가 없어진 파일을 가리켰고,
  그 뒤 8개 라운드가 전부 그 축 작업이었다. **쪼개기·개명 직후 반드시 돌린다.**

## 역방향 고아 검사

- 정방향(참조 → 파일 존재)만 보면 **재온보딩이 호출 줄을 날려도 통과한다** — 파일은 남고 부르는 데만 사라져 아무 에러도 안 난다.
- 실패로 처리하지 않는 이유: 원래 독립 실행용 자산일 수 있다(실측: 사례 C 의 스키마 조사 에이전트 2종).

## 시험 범위(1.9.0)

- 1.8.0 까지 에이전트 자체검증·QA 실측 줄이 `{{build_cmds}}`(전체)였다 — CO 하나에 전체 시험이
  «대상 수 × 2회 + 재구현 횟수» 돌았다(실측 사례 D: 웹 시험 8,269건 · CPU 약 1,000초).
- 연관 시험 명령을 돌려 0건이면 명령이 틀렸거나 경로가 안 맞는다 — 에이전트는 **0건을 통과로 읽는다.**
- 표 안의 「전체 시험」 칸은 정상이다. 검사는 **표 줄을 뺀** 자체검증·실측 절에 전체 시험 명령이 남았는지를 본다
  (1.9.0 의 검사는 표까지 grep 해 늘 실패했다 — 1.10.0 에서 고쳤다).

## 병행 레인

- `knowhow_dir_abs` 강제가 빠지면 QA 를 위임할 때 묶음이 안 따라간다. 절대경로는 **실행 시 계산**한다
  (1.9.0 은 온보딩한 사람의 절대경로를 커밋 파일에 박았다 — 팀원마다 틀렸다).
- 범위 줄 검사(「전체 시험은 합치기에서 한 번만 돈다」)가 빠지면 QA 가 전체 시험을 돌린다 —
  실측(사례 D): 그 한 줄을 빠뜨린 QA 두 번이 각각 8,2xx 건을 돌렸다.
- 합치기의 남은 프로세스 끝내기: 작업자가 띄운 부하용 프로세스 10개가 레인을 지운 뒤에도 하루 가까이 돌았다(사례 D).
  판정을 명령줄 전체로 하면 경로에 `claude` 가 든 레인(`.claude/worktrees/…`)의 node·시험 프로세스까지 살려 둔다 — 그래서 **이름(comm)만** 본다.
  명령줄은 비밀이 실릴 수 있어 찍지 않는다(`pgrep -f` 출력으로 토큰이 노출된 실측).
