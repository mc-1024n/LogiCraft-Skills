# {{skill_prefix}}-dispatch — {{project_name}} 수정 오케스트레이터

자유서술 수정요청 하나를 받아, **변경지시서(Change Order)를 파일로 남기고 → 영향 도메인 코드를 도메인 전용 에이전트로 구현**하는 프로젝트 전용 디스패처.

## ★ 핵심 원칙

1. **LogiCraft 설계·로컬 키트는 즉시 반영하지 않는다.** 수정사항을 **변경지시서(CO) 파일**(`{{change_orders_path}}CO-NNN-*.md`)에 자세히 기술만 하고, LogiCraft ITEM backfill 은 **나중에 배치**(`/{{skill_prefix}}-design-backfill`)로 한다. 이 스킬은 설계·키트를 안 건드린다.
2. **적용 상태는 마스터 파일로 관리** — `{{change_orders_path}}MASTER.md` 표에 CO 별·도메인별 구현/설계반영 상태.
3. **구현 에이전트는 로컬 키트를 SYNC 하지 않는다.** 메인이 CO 의 해당 도메인 변경 상세(`change_detail`)를 프롬프트로 직접 내려준다 → 에이전트는 **수정 모드**로 동작(`change_detail` 이 진실원).
<!-- IF code_boundary == package -->
4. **공유기반 주의** — 도메인들이 `core/`·`db/migrations/`·앱 진입점을 **공유**한다. 변경이 스키마/공유기반을 건드리면 도메인 에이전트가 못 고침 → **메인이 먼저 처리**(Phase 3.5) 후 도메인 fan-out.
<!-- ENDIF code_boundary -->
5. **오케스트레이션만.** 이 스킬은 직접 코드/ITEM 안 짬. 구현은 도메인 에이전트, QA 는 `{{prefix}}-qa-verifier`, 설계 backfill 은 별도 스킬.

### Phase 1 — 의도 파악  🚦게이트①
자유서술 요청을 **무엇을 / 왜 / 어느 범위**로 정리. 버그면 근본원인까지 코드에서 확인(대상 파일 grep/read). 애매하면 되묻는다.

### Phase 2 — 변경지시서(CO) 작성  (LogiCraft 대신)
1. **영향 도메인 판정** — 코드 기반. grep(traceability 태그는 `grep -ri '@design'` — 기본형 `@design` 과 어노테이션 `@DesignRef` 를 한 번에 잡는다 ·API 경로·`SCREEN-`/`API-`) + 도메인 매핑표 + 도메인 에이전트 특화지식. 한 변경이 여러 도메인·백/프론트에 걸치면 각각 분해.
<!-- IF code_boundary == package -->
   - ★ **공유기반 영향 체크**: 변경이 `core/`·`db/migrations/`·앱 진입점을 건드리는지 판정. 건드리면 CO §3 에 명시하고 **메인 선처리** 대상으로 표시.
<!-- ENDIF code_boundary -->
2. **CO 파일 작성** — `{{change_orders_path}}_TEMPLATE.md` 골격으로 `{{change_orders_path}}CO-NNN-{slug}.md`. CO 번호 = MASTER 표 최하단 +1.
   - ★ **도구 모르는 사람도 이것만 읽고 이해**하도록 자세히. §3 "도메인별 변경 상세"는 각 도메인 에이전트가 받아 구현할 만큼 구체적으로(대상 파일/심볼·변경·불변·주의).
   - §6 "관련 설계 ITEM"에 나중에 backfill 할 예상 ITEM 기록(지금 반영 안 함).
3. **MASTER 등록** — `MASTER.md` 표에 행 추가(상태 📝, 대상 도메인, 생성일, 설계반영 ⏳).

#### ★ QA 계획을 **게이트에서 합의**한다 (혼자 정하지 않는다)

등급·회귀 범위를 오케스트레이터가 속으로 정하면 **근거가 안 남고, 범위가 커져도 재판정을 안 한다.**
그래서 게이트 문구에 **세 줄**을 박는다. 사용자가 그 자리에서 조정할 수 있다.

**등급을 가르는 질문은 하나** — 「빌드·테스트가 그린인데도 **사용자 화면에서 터질 수 있는가**」

| 등급 | 대상 |
|---|---|
| **전수** | 물리명 rename · 스키마·마이그레이션 · 외부 계약 접점 · 인증/권한 · 캐시 정책 · **공용 컴포넌트** |
| **경량** | 정적으로 확정되는 것 — 주석·문서 · 로직 0 변경 · 설계 서술 |
| **생략** | 오타·문구 1줄 |

☠️ **등급을 올려야 하는 신호 — 착수 뒤에 이게 나타나면 «다시 판정»한다:**
**공용 컴포넌트·공용 모듈이 범위에 편입** / **물리명·스키마 변경** / **인증·권한** / **외부 계약**.
(실사고: 범위가 공용 부품까지 커졌는데 등급을 다시 안 매겨 경량으로 끝났다.)

★ **경량이어도 생략하면 안 되는 것 셋** — ①구현자 주장 수치의 **독립 재현** ②동시 진행 작업과의

### Phase 4 — 구현 fan-out

★ **노하우 묶음 지정** — 에이전트 본체에는 **색인**만 있고 주제별 노하우는 `{{knowhow_dir}}` 에 있다.
이번 변경에 관련될 묶음이 보이면 프롬프트에 **「이 묶음도 읽어라」로 «추가»**한다.

☠️ **빼지 마라. 추가만 한다.** 고르는 순간 **예상 가능한 것만 남는다** — 실측에서 「입력 상자 교체」로
보였던 건이 실제로 걸린 곳은 **공유 저장소 커밋 · 검사 기준선 · 창 안의 키 입력**이었다. 주제로
골랐으면 셋 다 빠졌을 것이다. 에이전트가 색인을 갖고 있으므로 **스스로 더 꺼내 읽을 수 있다** —
지정이 틀려도 치명적이지 않은 이유가 이것이다.

영향 대상마다 **한 메시지에서 병렬로** 해당 도메인 에이전트를 띄운다. **키트 SYNC 안 함** — CO 의 해당 도메인 상세를 프롬프트로 직접 전달(=수정 모드). 백/프론트 계약 의존이면 백엔드 회수 후 프론트(2 라운드).
```yaml
project_id: {{project_id}}
domain_id: DOMAIN-00N              # (프론트는 화면 소속 도메인)
code_root: "<이 도메인 code_root>"   # (프론트는 웹 code_root)
<!-- IF conventions_location == shared -->
conventions: "<repo>/{{conventions_path}}"
<!-- ENDIF conventions_location -->
change_order: "<repo>/{{change_orders_path}}CO-NNN-{slug}.md"   # 참조용
change_detail: |                    # ★ 구현 진실원 (수정 모드)
  <CO §3 의 이 도메인 섹션 전문 — 대상 파일·변경·불변·주의·수용기준>
target_hint: | <알면 대상 모듈/클래스/함수/화면. 모르면 생략>
```

### Phase 5.5 — 독립 QA 검증 ({{prefix}}-qa-verifier)
회수 직후 대상마다 `{{prefix}}-qa-verifier` 병렬. 구현이 red 면 QA 생략, 바로 재구현.

#### ★★ 검증은 **다른 모델**로 돈다 (온보딩에서 확정한 값)

**서열이 아니다.** 「비싼 쪽이 검증」이 아니라 **각자 놓치는 것이 다르다**는 게 전부다.
구현자가 못 본 것은 같은 모델의 검증자도 대개 못 본다 — 같은 방식으로 사고하기 때문이다.

| 항목 | 값 |
|---|---|
| **검증 모델·위임** | `{{qa_model}}` |
| **부르는 방법** | `{{qa_invoke}}` |
| **실패 시 대체 경로** | `{{qa_fallback}}` |
| **실패 판별 신호** | `{{qa_fail_signal}}` |

🔴 **판정은 «종료 코드»가 아니라 «verdict»로 한다.** 완주하고 `pass` 를 낸 판이 비정상 종료코드로
끝나는 일이 있다. 반대로 **아예 시작도 못 했는데 정상 종료처럼 보이는** 경우가 실제로 있었다
(없는 모델 이름 → 즉시 실패 → 래퍼가 조용히 종료 → 「통과」로 오독 → **검증이 0회 돌아간 채 라운드가 닫힘**).
⇒ `{{qa_fail_signal}}` 로 **「아예 안 돈 것」을 먼저 가려내고**, 그 경우 `{{qa_fallback}}` 으로 대체 실행한다.
⇒ ☠️ **대체 실행했다는 사실을 보고에 남겨라** — 교차 검증(다른 모델) 이점이 사라진 상태이므로
   그 라운드는 「구현·검증이 같은 계열」이라는 한계를 안고 간다. 숨기면 다음 사람이 오판한다.
⇒ 대체가 **연속 2회 이상이면 모델 설정 자체를 의심**하라.

#### ★★ 회귀 범위는 **2단으로 준다** — 그리고 「여기까지만」이라 쓰지 마라

범위를 안 주면 레포 전체를 훑는다. 그런데 **주는 순간 그 밖을 안 본다** — 양날이다.
그래서 문구를 이렇게 쓴다:

> 회귀 범위는 2단이다. **1차 = 변경 파일 그 자체**(diff 전건 정독).
> **2차 = 변경된 심볼을 «직접» 부르는 곳(1홉)** — 거기서 멈춘다. 2홉 이상은 전체 빌드·테스트가 덮는다.
> ☠️ 「안 본다」가 아니라 **「어디까지 봤는지 적는다」** — 1홉 목록과 판정을 열거하라.
> ☠️ **이 범위를 좁힌 근거를 함께 준다**(아래). 근거가 틀렸다고 판단되면 **그 근거 자체를 반증하고 보고하라.**

⚠️ **예외 — 이 제한을 걸지 마라**: 물리명 rename · 스키마 변경 · 공유 DB 접점.
컴파일이 파급을 안 잡으므로 전수 스윕이다.
```yaml
project_id: {{project_id}}
domain_id: DOMAIN-00N
code_root: "…/<이 도메인 code_root 또는 웹>"
<!-- IF conventions_location == shared -->
conventions: "<repo>/{{conventions_path}}"
<!-- ENDIF conventions_location -->
change_order: "…/{{change_orders_path}}CO-NNN-*.md"
change_detail: | <해당 도메인 변경 상세 — 수용기준·불변>
implemented: | <구현 에이전트가 보고한 변경 파일·요지>
claimed_verification: | <구현 에이전트가 주장한 결과 — QA 가 실측 대조>
changed_files: | <`git diff --name-only` 결과 — 1차 회귀 범위>
qa_scope: | <Phase 3 에서 합의한 등급·회귀 홉수 **그리고 그 근거**. 근거가 틀렸다고 보이면 반증하고 보고하라>
probe_axes: | <★ 오케스트레이터가 정한 «파고들 축». 비우지 마라 — 축이 비면 주어진 것만 검산하고 끝난다>
```

☠️ **축을 정해서 넘기는 건 오케스트레이터 몫이다.** 「무엇을 파야 하는가」는 CO 와 구현 결과를 다 본
메인이 안다. 축이 비면 **모델 탓이 아니라 지시 탓**이다.

☠️ **「갈음」을 허용하지 마라** — 못 하면 **왜 못 했는지와 무엇이 미검증으로 남는지**를 명시하게 하라.
- `pass`/`pass_with_notes` → Phase 6.
- `fail` → 해당 구현 에이전트에 issues+fix_hint 담아 재호출(최대 2라운드), 그래도 fail 이면 red 보고.
- `blocked`(실측 불가) → 정직 보고, 런타임 검증 잔여.

### Phase 5.9 — 노하우 반영 (에이전트 파일 갱신)  🚦게이트
회수한 각 에이전트 출력의 `notes_for_main.learned` 를 본다. **전부 비어있으면 건너뛴다**(보고에 "노하우 신규 없음").
- 있으면 항목별로 **사용자에게 제시** — 어느 에이전트의 `## 노하우` 에 무엇을 추가할지 + 근거(evidence)·재발조건.
- 동의한 항목만 해당 `{{prefix}}-d00N-implementer`(프론트는 `{{prefix}}-web-implementer`) 파일의 `## 노하우` 섹션에 **append**. 기존 항목은 **함부로 지우지 않는다**(축적이지 교체가 아님) — 단 아래 **상한 게이트**에 걸리면 정리한다.
- **QA(Phase 5.5)에서 fail → 재구현으로 드러난 함정도 후보**로 함께 올린다. 같은 지적이 CO 를 넘어 반복되면 노하우 1순위.
- 근거(evidence) 없는 항목은 반영하지 않는다(AI 추정 금지). 동의 못 받은 항목은 버리지 말고 CO §7 구현 로그에 남긴다.
- 도메인 특화 지침(설계 근거)과 혼동 금지 — 여기 쌓는 건 **구현하며 얻은 경험**이고, 설계에서 온 제약은 backfill 대상이다.

#### ★★ 노하우는 **나눠 담는다** — 본체 400줄이 넘으면 묶음을 하나 더 판다

☠️ **축적만 하면 성능이 떨어진다.** 에이전트는 매 호출마다 자기 파일을 통째로 읽고 시작하므로,
길어질수록 **고정 비용이 늘고 정작 중요한 항목이 묻힌다.**

**실측 근거(KLID)** — QA 노하우 660줄 · 화면 구현 노하우 **1,976줄**. 원인 셋:

2. 「라운드 섹션 만들지 마라」를 **적어 놓고도 3라운드 연속 어겼다.**
3. ☠️ **같은 함정이 9곳에 흩어져 적힌 숫자가 서로 달랐다**(선존 lint 오류 수 155·157·163).
   **작업자가 어느 걸 읽느냐로 판정이 갈린다.**

**구조 — 본체는 얇게, 주제는 묶음으로**

| 어디에 | 무엇을 |
|---|---|
| **에이전트 본체** | 절차·경계·출력 규약 + **매 라운드 필요한 게이트 판정** + **`## 노하우 색인`** |
| **`{{knowhow_dir}}`** | 주제별 묶음 — 색인이 「언제 읽어야 하나」와 함께 가리킨다 |
| **`{{knowhow_archive_dir}}`** | 정리 시 원문 보관 |

**☠️ 처음엔 묶음이 0개다 — 그래서 첫 노하우가 본체에 붙고, 그게 쌓여 1,000줄이 된다**

「주제 묶음에 붙여라」인데 **붙일 묶음이 없는** 상태로 시작한다. 그대로 두면
전부 본체 「상시」 절에 쌓이고, 몇 달 뒤 **정리 대상**이 된다. 그걸 막는 규칙:

- **상시 절이 «항목 5개» 또는 «120줄» 을 넘으면 그때 첫 묶음을 판다.**
  400줄까지 기다리지 마라 — 그때는 이미 주제가 엉켜 가르기 어렵다.
- 묶음을 팔 때는 **가장 덩어리가 큰 주제 하나**부터. 이름은 `{{knowhow_dir}}<prefix>-<주제>.md`.
- 묶음을 만들면 **색인 표에 한 줄**을 추가한다 — 주제 · 파일 · **「언제 읽나」**.
  ☠️ 「언제 읽나」가 비면 에이전트가 판단할 근거가 없어 **아무도 안 읽는다.**
- **상시 절에 남길 것** = 주제와 무관하게 **매 라운드 적용되는 것**
  (게이트 판정법 · 이 레포의 검사 기준선 · 사고 이력이 있는 축).

**규칙**
- 노하우 반영 **직후 본체 줄 수를 센다**. `wc -l` 이 **400줄 초과**면 게이트를 연다.
  (개수가 아니라 **줄 수** — 항목 55개에 660줄이었다. 개수로는 안 잡힌다. **묶음은 세지 않는다.**)
- **1순위 처방은 「정리」가 아니라 「묶음을 하나 더 파기」다.** 주제가 뚜렷한 덩어리를
  `{{knowhow_dir}}` 로 옮기고 본체에는 **색인 한 줄**만 남긴다.
- ☠️ **뒤로 미루는 것만으로는 소용없다** — 파일을 통째로 읽으므로 **별도 파일로 분리**해야 실제로 준다.
- 새 노하우는 **주제에 붙인다.** ☠️ **라운드 섹션을 만들지 마라** — 이 규칙은 **지켜지지 않는 쪽으로
  기운다.** 쓰기 전에 **색인의 주제 제목부터 읽어라.**
- 같은 함정이 이미 있으면 **새로 쓰지 말고 그 항목을 보강**하라. 흩어지면 숫자가 갈린다.
- 게이트에서 **사용자에게 묻는다**(자동 정리 금지). 제시할 것: 본체 줄 수 · 주제별 분량 ·
  **묶음 후보와 근거** · 삭제 후보와 근거(완료된 캠페인 / 이미 흡수됨 / 중복).
- ☠️ **지우는 게 아니라 «보관 후 정리»** — 원문을
  `{{knowhow_archive_dir}}<에이전트>-노하우전문-<YYYYMMDD>.md` 로 먼저 뜬다.
  머리말에 **보관본 경로와 정리 경위**를 적는다.
**★ 묶음에도 상한이 있다 — 600줄** 

묶음은 「필요할 때만」 읽으니 본체보다 관대해도 되지만, **무한은 아니다.**
실측(LogiCraft 재온보딩): 본체를 3,325 → 565 로 줄였는데 **묶음 하나가 1,306줄**이 됐다.
그 묶음이 한 번 지정되면 **565 + 1,306 = 1,871** — 줄인 효과가 그 자리에서 상쇄된다.

- **600줄 초과면 «더 잘게 쪼갤지» 묻는다**(게이트 · 자동 금지).
- ☠️ **쪼개는 방식은 «평면 세분화»다. 묶음 안에 또 묶음을 두지 마라.**
  계층을 두면 색인이 2단이 되어 **에이전트가 「어느 하위를 읽을지」를 또 판단**해야 한다 —
  줄이려던 비용이 다시 는다. **색인은 항상 한 단**으로 둔다.
- **600줄이 넘었다는 건 대개 주제를 굵게 잡았다는 뜻**이다. 안을 열어 보면 서로 다른 상황에서
  읽는 것들이 뭉쳐 있다(실측: 「테스트설계」 안에 **변이 설계 · 구조 함정 · e2e** 가 함께).
  ⇒ 이름을 `<주제>-<하위>` 로 갈라 **평면으로** 늘린다. 색인엔 줄이 하나 더 늘 뿐이다.
- 색인의 **「언제 읽나」가 갈라지지 않으면** 쪼개도 소용없다 — 같은 상황에서 둘 다 읽게 된다.
  쪼개기 전에 **「이 둘은 다른 때 읽는가」**를 먼저 확인하라.

- ☠️ **삭제·이동 전 «제목 단위 대조»로 유실 0건 확인.** 「보관했으니 괜찮다」로 넘기지 마라.
  묶음으로 옮긴 경우 **본체 + 묶음 합산**으로 대조한다.
