# {{skill_prefix}}-dispatch — {{project_name}} 수정 오케스트레이터

자유서술 수정요청 하나를 받아, **변경지시서(Change Order)를 파일로 남기고 → 영향 도메인 코드를 도메인 전용 에이전트로 구현**하는 프로젝트 전용 디스패처.

## ★ 핵심 원칙

1. **LogiCraft 설계·로컬 키트는 즉시 반영하지 않는다.** 수정사항을 **변경지시서(CO) 파일**(`{{change_orders_path}}CO-NNN-*.md`)에 자세히 기술만 하고, LogiCraft ITEM backfill 은 **나중에 배치**(`/{{skill_prefix}}-design-backfill`)로 한다. 이 스킬은 설계·키트를 안 건드린다.
2. **적용 상태는 마스터 파일로 관리** — `{{change_orders_path}}MASTER.md` 표에 CO 별·도메인별 구현/설계반영 상태.
3. **구현 에이전트는 로컬 키트를 SYNC 하지 않는다.** 메인이 CO 의 해당 도메인 변경 상세(`change_detail`)를 프롬프트로 직접 내려준다 → 에이전트는 **수정 모드**로 동작(`change_detail` 이 진실원).
<!-- IF code_boundary == package -->
4. **공유기반 주의** — 도메인들이 {{shared_base}} 을(를) **공유**한다. 변경이 스키마/공유기반을 건드리면 도메인 에이전트가 못 고침 → **메인이 먼저 처리**(Phase 3.5) 후 도메인 fan-out.
<!-- ENDIF code_boundary -->
5. **오케스트레이션만.** 이 스킬은 직접 코드/ITEM 안 짬. 구현은 도메인 에이전트, QA 는 `{{prefix}}-qa-verifier`, 설계 backfill 은 별도 스킬.

## 파이프라인

### Phase 1 — 의도 파악  🚦게이트①
자유서술 요청을 **무엇을 / 왜 / 어느 범위**로 정리. 버그면 근본원인까지 코드에서 확인(대상 파일 grep/read). 애매하면 되묻는다.
확인: *"요청 이해: [정리]. 변경지시서로 정리하고 구현까지 진행할까요?"*

### Phase 2 — 변경지시서(CO) 작성  (LogiCraft 대신)
1. **영향 도메인 판정** — 코드 기반. grep(traceability 태그는 `grep -ri '@design'` — 기본형 `@design` 과 어노테이션 `@DesignRef` 를 한 번에 잡는다 ·API 경로·`SCREEN-`/`API-`) + 도메인 매핑표 + 도메인 에이전트 특화지식. 한 변경이 여러 도메인<!-- IF frontend_track -->·백/프론트<!-- ENDIF frontend_track -->에 걸치면 각각 분해.
<!-- IF code_boundary == package -->
   - ★ **공유기반 영향 체크**: 변경이 공유기반({{shared_base}})을 건드리는지 판정. 건드리면 CO §3 에 명시하고 **메인 선처리** 대상으로 표시.
<!-- ENDIF code_boundary -->
2. **CO 파일 작성** — `{{change_orders_path}}_TEMPLATE.md` 골격으로 `{{change_orders_path}}CO-NNN-{slug}.md`. CO 번호 = MASTER 표 최하단 +1.
   - ★ **도구 모르는 사람도 이것만 읽고 이해**하도록 자세히. §3 "도메인별 변경 상세"는 각 도메인 에이전트가 받아 구현할 만큼 구체적으로(대상 파일/심볼·변경·불변·주의).
   - §6 "관련 설계 ITEM"에 나중에 backfill 할 예상 ITEM 기록(지금 반영 안 함).
3. **MASTER 등록** — `MASTER.md` 표에 행 추가(상태 📝, 대상 도메인, 생성일, 설계반영 ⏳).

#### ☠️☠️ CO 에 「실측된 N곳」 표를 주면 **그 표가 완료 근거로 읽힌다**

실사고(2026-09): 메인이 식별자 재번호 영향을 **실측 4곳**으로 표에 적어 넘겼다.
구현자가 전수 grep 을 돌리자 **실제로는 45곳**이었다 — 시험 케이스 판 2개에만 41곳.
**표만 믿었으면 41곳이 구 번호로 남는다.**

식별자 인용은 **네 층**에 흩어지고, 요약 파일 grep 은 **첫 층만** 잡는다:

1. 요약·헬퍼 파일 ← 메인이 보통 여기까지만 실측한다
2. `expected` 등 단언 문자열
3. 절차 구분 주석
4. **JSDoc·docstring 헤더의 given/when/then 인덱스**

☠️ 특히 결론표 행이 **template literal / f-string**(`` `| 규칙8 — … | ${row} |` ``) 안에 있으면
**단순 문자열 grep 목록에 안 걸린다.**

⇒ **CO 에 실측 목록을 넣을 때는 반드시 이렇게 쓴다:**
> 「아래는 실측으로 찾은 것이다. **이것만 고치지 말고 전수 grep 으로 누락을 재확인하라.**
>  수용기준은 「표의 N곳 수정」이 아니라 **「구 번호 잔존 0건」**이다.」

그리고 **수용기준에 grep 명령 자체를 적어** 채점이 성립하게 한다.

#### ★ QA 계획을 **게이트에서 합의**한다 (혼자 정하지 않는다)

**등급을 가르는 질문은 하나** — 「빌드·테스트가 그린인데도 **사용자 화면에서 터질 수 있는가**」

| 등급 | 대상 |
|---|---|
| **전수** | 물리명 rename · 스키마·마이그레이션 · 외부 계약 접점 · 인증/권한 · 캐시 정책 · **공용 컴포넌트** |

### Phase 4 — 구현 fan-out

★ **노하우 전달 — 고르지 말고, 읽기를 «검사»한다** (2026-09-19 개정)

에이전트 본체에는 **색인만** 있고 주제별 노하우는 `{{knowhow_dir}}` 묶음에 있다.
**두 가지 고르기가 모두 실패했다**는 것이 이 절의 전제다:

| 누가 고르나 | 실측 결과 |
|---|---|
| **메인**이 주제로 골라 지정 | 「입력 상자 교체」로 보인 건이 실제로 걸린 곳은 **공유 저장소 커밋 · 검사 기준선 · 창 안의 키 입력** — 주제로 골랐으면 셋 다 빠졌다 |
| **에이전트**가 색인 보고 알아서 | 색인 조건에 **정확히 해당**하는 작업에서도 **열람 0건**(LogiCraft CO-163 · 구현 3 · QA 2) |

⇒ 그래서 고르기를 **요청에서 검사로** 바꾼다. 고르는 주체는 **에이전트**(예측 못 하는 걸 메인이 대신 못 한다),
   대신 **안 고르면 드러나게** 한다:

1. 프롬프트에 **`knowhow_dir_abs: <묶음 디렉터리 절대경로>`** 를 반드시 넣는다.
   ☠️ 상대경로로 주지 마라 — 다른 모델로 위임되면 작업 디렉터리가 달라 못 찾는다.
2. 프롬프트에 **한 줄을 명령형으로** 넣는다:
   > 「착수 전에 본체의 `## 노하우 색인` 을 **모든 행** 훑고, 해당 묶음을 **실제로 열어** 읽어라.
   >  작업 도중 색인의 «이 행동»을 하려는 순간 그 행을 다시 봐라. 출력 `knowhow_read` 는 **필수**다.」
   ☠️ 「관련 있으면」·「참고하라」 같은 권유형 금지 — 그 문구로 0건이 나왔다.
3. 메인이 따로 떠오르는 묶음이 있으면 **추가 지정만** 한다. **빼지 마라.**
4. **회수 때 대조**한다(Phase 5 ★ 노하우 열람 게이트).

영향 대상마다 **한 메시지에서 병렬로** 해당 도메인 에이전트를 띄운다. **키트 SYNC 안 함** — CO 의 해당 도메인 상세를 프롬프트로 직접 전달(=수정 모드).<!-- IF frontend_track --> 백/프론트 계약 의존이면 백엔드 회수 후 프론트(2 라운드).<!-- ENDIF frontend_track -->

#### ☠️☠️ **코디네이터가 준 자료를 에이전트가 의심하게 만들어라**

실사고(2026-09): 메인이 만든 작업 파일에 결함이 **두 건** 있었고, **둘 다 에이전트가 잡았다.**

| 결함 | 어떻게 드러났나 |
|---|---|
| 스키마 추출에 `LOWER()` 를 씌워 **대소문자를 뭉갬** | 한 레인이 **원본 DDL·ORM 매핑으로 교차확인**해 바로잡음. 다른 레인은 그대로 믿었다 |
| **A DB 용 설계서**인데 **B DB 의 컬럼 목록**을 줌 | 그 레인이 DBMS 종류·타입·컬럼 수로 이상을 감지하고 **해당 DB 를 직접 조회** |

두 번째는 결과가 컸다 — **감사 27건이 통째로 오탐**임이 드러났다(엉뚱한 DB 와 대조하고 있었다).

⇒ **위임 프롬프트에 반드시 박아라:**
> 「이 작업 파일은 **참고 자료**다. 진실원은 **실물**이다. 값이 이상하면 **원본을 직접 다시 재라.**
>  코디네이터 자료와 실물이 어긋나면 **실물을 따르고 그 사실을 보고**하라.」

⇒ 그리고 **실물을 잴 수단을 프롬프트에 같이 줘라**(DB 접속 정보·조회 명령 등).
   **자료만 주면 의심할 방법이 없다** — 「의심하라」는 말만으로는 아무 일도 일어나지 않는다.

### Phase 5 — 회수
각 에이전트 출력 YAML(implemented/verification/tracking/design_facts/notes_for_main) 취합. red 그대로.

#### ★ 설계 사실 옮겨 적기 (`design_facts` → CO §6)
각 구현 에이전트의 `design_facts`(코드에서 확인한 구현 사실 — `{item, field, value, basis}`)를 **CO §6 「설계 사실」** 에
`- ITEM.칸: 값 — 근거` 한 줄씩 옮긴다. 설계 backfill 이 이것을 **칸 값**으로 그대로 넘긴다 — 코드를 다시 추적하지 않게.
- 근거 없는 줄·실재 확인 안 된 ID 는 옮기지 않는다(AI 추정 금지). 비어 있으면 「설계 사실 없음(구현 사실 칸 해당 없음)」 한 줄.
- ☠️ 여기서 LogiCraft ITEM 을 직접 고치지 않는다 — 설계 반영은 backfill 몫이다.<!-- IF code_boundary == package --> notes 의 needs_core_change 가 뒤늦게 나오면 Phase 3.5 로 되돌아감.<!-- ENDIF code_boundary -->

#### ★ 노하우 열람 게이트 (회수 직후 · 구현·QA 공통)

각 출력의 `knowhow_read` 를 본다.

| 상태 | 처리 |
|---|---|
| **필드 자체가 없음 / 빈 값** | 그 에이전트를 **되돌려 보낸다**(구현 결과는 보존 · 「색인을 훑고 knowhow_read 를 채워라」만 재지시) |
| `skipped` 가 색인 행 수보다 적음 | 훑지 않은 행이 있다 — 되돌려 보낸다 |
| `used` 에 **`how` 가 없음** | 머리말 규칙을 **잰 적이 없다**는 뜻 — 되돌려 보낸다(`how` 만 채우면 된다) |
| `how: full` 인데 `matched` 가 **없거나 4 미만** | 조건 미달 전문 읽기. **되돌리지는 않는다**(결과는 유효) — **세어서 Phase 5.9 에 올린다** |
| 같은 묶음이 **2 라운드 연속** `how: full` | 그 묶음은 머리말로 못 거른다 — **쪼갠다**(Phase 5.9 처방) |
| 채워져 있음 | **전사본과 대조**한다 ↓ |

**대조** — 적었다고 믿지 마라. 전사본에서 **실제 열람**을 센다:
```python
# 서브에이전트 전사본에서 _knowhow 묶음을 «Read» 로 연 것만 (ls·wc 는 제외된다)
# ★ file_path 뿐 아니라 offset/limit 까지 뽑는다 — 「열었나」가 아니라 «어떻게 열었나» 를 봐야
#   머리말 규칙이 지켜졌는지 알 수 있다. limit 이 없는 Read 는 그 줄부터 EOF 까지 = 사실상 전문 읽기다.
import re,glob,os
B=os.path.expanduser("~/.claude/projects/<프로젝트 슬러그>/<세션id>/subagents")
for f in sorted(glob.glob(B+"/agent-*.jsonl")):
    t=open(f,errors="ignore").read()
    for m in re.finditer(r'\{"file_path":"([^"]*_knowhow/[^"]*)"([^{}]*)\}', t):
        name=m.group(1).split("_knowhow/")[1]; rest=m.group(2)
        off=re.search(r'"offset":\s*(\d+)',rest); lim=re.search(r'"limit":\s*(\d+)',rest)
        kind=("머리말" if (lim and int(lim.group(1))<=25 and not off)
              else "항목"  if (off and lim)
              else "★전문(limit 없음)")
        print(os.path.basename(f), name, kind,
              f"offset={off.group(1) if off else '-'} limit={lim.group(1) if lim else '없음'}")
```
opencode 위임분은 로그(`.claude/opencode-runs/<라벨>.txt`)에서 묶음 파일명 grep.

☠️☠️ **대조 결과를 결론으로 쓰기 전에 «측정기 자체»를 검산하라.**
실측(LogiCraft 2026-09-20) — 「읽은 척 3건」으로 보고했다가 전수 재검증하니 **2건이 이쪽의 측정 오류**였다.
그 오판 위에 **에이전트 본체 8개를 고치고** 핸드오프에 핵심 발견으로 적었다.

| 무엇을 틀렸나 | 어떻게 막나 |
|---|---|
| `grep \| sed \| sort -u \| head` 로 세고 **출력이 잘린 것을 검산 안 함** | `head` 로 자르지 마라. 센 뒤 **총계와 목록 길이가 맞는지** 본다 |
| **`✗ … failed` 를 「못 읽었다」로 해석** — 실제로는 **이미 올바른 이름으로 읽은 뒤** 이어 읽으려다 이름을 틀린 것 | 실패 줄 **앞뒤를 읽어** 성공 열람이 선행하는지 본다 |

★ 그래서 **`used` 에 줄 번호를 요구**한다 — 줄 번호는 파일을 열어야만 알 수 있어 **검산이 싸다.**
  (실측: 인용 11건 중 10건이 해당 줄과 정확히 일치.)
☠️ **판정 품질과 보고 정직성은 별개다.** 같은 라운드에서 QA 가 8축을 다 해내고 구현자의 수치 오류까지 잡았는데,
  자기 보고에는 같은 종류의 부정확이 있었다. **결과가 좋았다고 그 보고가 참이 되지는 않는다.**

- ☠️ **보고한 `how` 와 실제 Read 인자가 어긋나면 그것도 결함**이다 — `how: items` 라고 적었는데
  전사본에 `limit` 없는 Read 가 있으면 **전문을 읽고 항목만 인용한 것**이다. 「읽은 척」보다 흔하다.
  ★ 단, 결론 내기 전에 **측정기부터 검산하라**(아래 실사고). 정규식이 한 건이라도 못 잡으면 무고가 된다.
- ☠️ **`read` 에 적은 묶음이 실제 열람에 없으면 결함**이다 — 보고에 명시하고 그 라운드 노하우 반영(Phase 5.9) 때 함께 본다.
- ★ 이 게이트의 목적은 벌이 아니라 **측정**이다. 라운드마다 「묶음 열람 수」를 보고에 한 줄 남겨라.
  재온보딩 직후 **0건**이 기준선이다 — 이 수치가 늘어야 노하우가 실제로 전달되고 있는 것이다.

### Phase 5.5 — 독립 QA 검증 ({{prefix}}-qa-verifier)
회수 직후 대상마다 `{{prefix}}-qa-verifier` 병렬. 구현이 red 면 QA 생략, 바로 재구현.
★ **QA 프롬프트에도 `knowhow_dir_abs`(절대경로)와 「색인 전 행 훑기 · `knowhow_read` 필수」를 넣는다.**
  ☠️ 다른 모델로 위임하면 **본체 한 파일만 미러로 복사**되고 묶음은 따라가지 않는다 —
  경로를 안 주면 QA 는 묶음의 존재조차 모른다(LogiCraft 재온보딩 후 QA 에서 약 875줄이 사라진 원인).

#### ★★ 검증은 **다른 모델**로 돈다 (온보딩에서 확정한 값)

**서열이 아니다.** 「비싼 쪽이 검증」이 아니라 **각자 놓치는 것이 다르다**는 게 전부다.
구현자가 못 본 것은 같은 모델의 검증자도 대개 못 본다 — 같은 방식으로 사고하기 때문이다.

| 항목 | 값 |
|---|---|
| **검증 모델·위임** | `{{qa_model}}` |
| **부르는 방법** | `{{qa_invoke}}` |
| **실패 시 대체 경로** | `{{qa_fallback}}` |
| **실패 판별 신호** | `{{qa_fail_signal}}` |

🔴 **판정은 «종료 코드»가 아니라 «verdict»로 한다.** 완주하고 `pass` 를 낸 판이 비정상 종료코드로
끝나는 일이 있다. 반대로 **아예 시작도 못 했는데 정상 종료처럼 보이는** 경우가 실제로 있었다
(없는 모델 이름 → 즉시 실패 → 래퍼가 조용히 종료 → 「통과」로 오독 → **검증이 0회 돌아간 채 라운드가 닫힘**).
⇒ `{{qa_fail_signal}}` 로 **「아예 안 돈 것」을 먼저 가려내고**, 그 경우 `{{qa_fallback}}` 으로 대체 실행한다.
⇒ ☠️ **대체 실행했다는 사실을 보고에 남겨라** — 교차 검증(다른 모델) 이점이 사라진 상태이므로
   그 라운드는 「구현·검증이 같은 계열」이라는 한계를 안고 간다. 숨기면 다음 사람이 오판한다.
⇒ 대체가 **연속 2회 이상이면 모델 설정 자체를 의심**하라.

🔴 **반대 방향의 실패도 있다 — 완주했는데 verdict 를 못 쓰고 끊긴 판.**
30분 이상 돈 QA 가 verdict 블록을 쓰기 직전 **SIGTERM(exit 143)** 으로 종료된 사례가 있다(원인 미상).
`{{qa_fail_signal}}` 만 보면 「실패」로 분류되지만 **실측은 이미 다 끝나 있었다.**
⇒ **재실행하지 말고 로그에서 판정을 회수하라** — 실행 로그에 전건 대조표·통과표가 남아 있다.
   재실행은 **시험 데이터만 또 쌓고** 30분을 다시 쓴다.
⇒ 그래서 QA 위임은 **항상 로그를 파일로 남기도록** 부른다(`> qa-out.log 2>&1`).
   로그가 없으면 이 회수가 불가능해지고, 그 라운드는 재실행 외에 선택지가 없다.

#### ★ QA 에도 «묶음 경로»를 준다 — 위임하면 묶음이 안 따라간다

QA 프롬프트에 **`knowhow_dir_abs: {{knowhow_dir_abs}}`** 와
「색인 전 행 훑기 · `knowhow_read` 필수」 한 줄을 **반드시** 넣는다.

☠️ **외부 도구로 위임하면 본체 «한 파일»만 미러로 복사되고 묶음은 따라가지 않는다.**
경로를 안 주면 QA 는 **묶음의 존재조차 모른다** — 실측: 재온보딩으로 QA 본체가 얇아진 뒤
**약 875줄이 QA 쪽에서 사라졌고**, 그 라운드 QA 의 묶음 열람은 **0건**이었다.
☠️ **상대경로로 주지 마라** — 위임 러너는 작업 디렉터리가 다를 수 있다. **절대경로**다.

#### ★★ 회귀 범위는 **2단으로 준다** — 그리고 「여기까지만」이라 쓰지 마라

범위를 안 주면 레포 전체를 훑는다. 그런데 **주는 순간 그 밖을 안 본다** — 양날이다.
그래서 문구를 이렇게 쓴다:

> 회귀 범위는 2단이다. **1차 = 변경 파일 그 자체**(diff 전건 정독).
> **2차 = 변경된 심볼을 «직접» 부르는 곳(1홉)** — 거기서 멈춘다. 2홉 이상은 전체 빌드·테스트가 덮는다.
> ☠️ 「안 본다」가 아니라 **「어디까지 봤는지 적는다」** — 1홉 목록과 판정을 열거하라.
> ☠️ **이 범위를 좁힌 근거를 함께 준다**(아래). 근거가 틀렸다고 판단되면 **그 근거 자체를 반증하고 보고하라.**

⚠️ **예외 — 이 제한을 걸지 마라**: 물리명 rename · 스키마 변경 · 공유 DB 접점.
컴파일이 파급을 안 잡으므로 전수 스윕이다.
```yaml
project_id: {{project_id}}
domain_id: DOMAIN-00N
code_root: "…/<이 도메인 code_root 또는 웹>"
<!-- IF conventions_location == shared -->

<!-- ENDIF conventions_location -->
```

⇒ **QA 프롬프트를 조립한 뒤 `grep knowhow_dir_abs` 로 실렸는지 확인**하고 나서 띄운다.

- `pass`/`pass_with_notes` → Phase 6.
- `fail` → 해당 구현 에이전트에 issues+fix_hint 담아 재호출(최대 2라운드), 그래도 fail 이면 red 보고.
- `blocked`(실측 불가) → 정직 보고, 런타임 검증 잔여.
> 규모/리스크가 아주 낮으면(오타·문구 1줄) QA 생략 가능하나 **기본은 실행**.

#### ★ QA 가 **CO 본문의 사실관계를 뒤집을 수 있다** — 정정하고 기록하라

실사고(2026-09): CO 가 「배포 양식 그대로면 업로드가 반려된다」고 적었으나 **거짓**이었다.
루프 인덱스가 두 루프에 공유·미초기화라 **헤더 검증 2종이 실운영에서 도달 불가**였고,
사용자가 본 반려는 사실 **다른 경로의 500** 이었다(QA 가 A/B + 양성 대조군으로 확정).

⇒ QA 의 `adversarial` 보고에 **CO 전제를 반증하는 내용**이 있으면
   **CO 본문에 정정문을 박아라.** 안 그러면 **다음 라운드가 같은 오해 위에서 작업한다.**
⇒ 그리고 그렇게 드러난 **선존 결함은 별건으로 이월**하라 — 고치는 순간 지금까지 통과하던 입력이
   새로 반려되기 시작하므로 **영향 평가가 따로 필요**하다. 이번 CO 에 끼워 넣지 마라.

### Phase 5.9 — 노하우 반영 (에이전트 파일 갱신)  🚦게이트
회수한 각 에이전트 출력의 `notes_for_main.learned` 를 본다. **전부 비어있으면 건너뛴다**(보고에 "노하우 신규 없음").

- ☠️☠️ **항목을 붙였으면 «그 자리에서» 머리말을 다시 만든다** — `python3 {{knowhow_dir}}_gen-headnote.py`.

실측(LogiCraft CO-164) — QA 가 `테스트설계-e2e` 를 「브라우저 검증이라 무관」으로 건너뛰었는데,

**「초크포인트 배선 검사가 사람이 열거한 호출처만 보면 새 통로가 조용하다」** 2건이 들어 있었다.

⇒ 이런 항목은 **읽힐 묶음으로 옮긴다**(위 예는 무보호·검출기 쪽). 색인의 「이 행동을 하기 전」도 함께 고친다.
☠️ 이것이 **이 체계의 유일한 자기교정 경로**다 — 건너뛰기 판단은 계속 에이전트 몫이므로,

#### ★★ 노하우는 **나눠 담는다** — 본체 400줄이 넘으면 묶음을 하나 더 판다

☠️ **축적만 하면 성능이 떨어진다.** 에이전트는 매 호출마다 자기 파일을 통째로 읽고 시작하므로,
길어질수록 **고정 비용이 늘고 정작 중요한 항목이 묻힌다.**

**실측 근거(KLID)** — QA 노하우 660줄 · 화면 구현 노하우 **1,976줄**. 원인 셋:
1. 통합해 놓고 **원본 302줄을 안 지웠다** — 같은 내용이 두 벌.
2. 「라운드 섹션 만들지 마라」를 **적어 놓고도 3라운드 연속 어겼다.**
3. ☠️ **같은 함정이 9곳에 흩어져 적힌 숫자가 서로 달랐다**(선존 lint 오류 수 155·157·163).
   **작업자가 어느 걸 읽느냐로 판정이 갈린다.**

**구조 — 본체는 얇게, 주제는 묶음으로**

| 어디에 | 무엇을 |
|---|---|
| **에이전트 본체** | 절차·경계·출력 규약 + **매 라운드 필요한 게이트 판정** + **`## 노하우 색인`** |
| **`{{knowhow_dir}}`** | 주제별 묶음 — 색인이 「언제 읽어야 하나」와 함께 가리킨다 |
| **`{{knowhow_archive_dir}}`** | 정리 시 원문 보관 |

**☠️ 처음엔 묶음이 0개다 — 그래서 첫 노하우가 본체에 붙고, 그게 쌓여 1,000줄이 된다**

「주제 묶음에 붙여라」인데 **붙일 묶음이 없는** 상태로 시작한다. 그대로 두면
전부 본체 「상시」 절에 쌓이고, 몇 달 뒤 **정리 대상**이 된다. 그걸 막는 규칙:

- **상시 절이 «항목 5개» 또는 «120줄» 을 넘으면 그때 첫 묶음을 판다.**
  400줄까지 기다리지 마라 — 그때는 이미 주제가 엉켜 가르기 어렵다.
- 묶음을 팔 때는 **가장 덩어리가 큰 주제 하나**부터. 이름은 `{{knowhow_dir}}<prefix>-<주제>.md`.
- 묶음을 만들면 **색인 표에 한 줄**을 추가한다 — **이 행동을 하기 전** · 파일 · 무엇이 있나.
  ☠️ **주제가 아니라 «행동»으로 건다**(예: 「`git stash`·`checkout --` 를 치기 전」·「실 DB 에 쓰기 전」).
     주제는 착수 때 예측해야 걸리지만, 행동은 **그 행동을 하려는 순간** 걸린다.
- **상시 절에 남길 것** = 주제와 무관하게 **매 라운드 적용되는 것**
  (게이트 판정법 · 이 레포의 검사 기준선 · 사고 이력이 있는 축).

**규칙**
- 노하우 반영 **직후 본체 줄 수를 센다**. `wc -l` 이 **400줄 초과**면 게이트를 연다.
  (개수가 아니라 **줄 수** — 항목 55개에 660줄이었다. 개수로는 안 잡힌다. **묶음은 세지 않는다.**)
- **1순위 처방은 「정리」가 아니라 「묶음을 하나 더 파기」다.** 주제가 뚜렷한 덩어리를
  `{{knowhow_dir}}` 로 옮기고 본체에는 **색인 한 줄**만 남긴다.
- ☠️ **뒤로 미루는 것만으로는 소용없다** — 파일을 통째로 읽으므로 **별도 파일로 분리**해야 실제로 준다.
- 새 노하우는 **주제에 붙인다.** ☠️ **라운드 섹션을 만들지 마라** — 이 규칙은 **지켜지지 않는 쪽으로
  기운다.** 쓰기 전에 **색인의 주제 제목부터 읽어라.**
- 같은 함정이 이미 있으면 **새로 쓰지 말고 그 항목을 보강**하라. 흩어지면 숫자가 갈린다.
- 게이트에서 **사용자에게 묻는다**(자동 정리 금지). 제시할 것: 본체 줄 수 · 주제별 분량 ·
  **묶음 후보와 근거** · 삭제 후보와 근거(완료된 캠페인 / 이미 흡수됨 / 중복).
- ☠️ **지우는 게 아니라 «보관 후 정리»** — 원문을
  `{{knowhow_archive_dir}}<에이전트>-노하우전문-<YYYYMMDD>.md` 로 먼저 뜬다.
  머리말에 **보관본 경로와 정리 경위**를 적는다.
**★ 묶음에도 상한이 있다 — 600줄** 

묶음은 「필요할 때만」 읽으니 본체보다 관대해도 되지만, **무한은 아니다.**
실측(LogiCraft 재온보딩): 본체를 3,325 → 565 로 줄였는데 **묶음 하나가 1,306줄**이 됐다.
그 묶음이 한 번 지정되면 **565 + 1,306 = 1,871** — 줄인 효과가 그 자리에서 상쇄된다.

#### ☠️ 600줄은 «쪼갤 이유»가 아니다 — **검토를 시작할 신호**다 (2026-09-19 개정)

크기를 결정 기준으로 쓰면 틀린다. **쪼개서 아끼려면 전제가 필요하다** — 쪼갠 조각이
**서로 다른 순간에** 필요해야 한다. 같은 순간에 다 필요하면 어차피 다 읽으므로 총량은 그대로이고,
**색인 행만 늘어 훑을 것이 많아진다.**

★ 실측이 그 전제를 지지하지 않는다(LogiCraft CO-164): QA 가 묶음 **10종 중 8종**을 읽었고,
노하우 항목 261개 중 **86.6%가 읽힌 묶음 안**에 있었다. **필요가 좁지 않고 넓다** —
넓게 필요한 것을 잘게 갈라도 결국 다 읽는다.

☠️ 그리고 쪼개기에는 **실증된 실패 방식**이 있다 — 2차 재온보딩이 600줄 상한으로 쪼개면서
본체 참조를 안 고쳐 **가장 강한 읽기 지시가 없어진 파일을 가리켰다**(그 뒤 8라운드가 그 축 작업이었다).

**⇒ 순서를 지켜라. 쪼개기는 마지막이다.**

| 순서 | 무엇 | 왜 먼저인가 |
|---|---|---|
| **1** | **중복 정리** | 전달을 **하나도 해치지 않고** 변동비만 줄인다. 실측: 한 에이전트 노하우 660줄 중 **302줄이 순수 중복**(같은 내용 두 벌)이었다 |
| **2** | **잘못 놓인 항목 재배치** | **전달과 비용을 동시에** 고친다 — 안 읽히던 항목이 읽히는 묶음으로 가고, 원래 묶음은 가벼워진다. 후보는 `knowhow_read.skipped` 사유에서 나온다 |
| **3** | **그래도 크면 쪼개기** | 판정 질문은 크기가 아니라 **「이 안의 내용이 서로 다른 순간에 필요한가」**. 45,000자여도 한 순간에 다 필요하면 **두고**, 15,000자여도 두 순간으로 갈리면 **쪼갠다** |

☠️ 쪼갠 직후에는 **끊긴 참조 검사**를 반드시 돌린다(본체·스킬이 가리키는 `_knowhow/*.md` 실재).

- **600줄 초과면 «더 잘게 쪼갤지» 묻는다**(게이트 · 자동 금지).
- ☠️ **쪼개는 방식은 «평면 세분화»다. 묶음 안에 또 묶음을 두지 마라.**
  계층을 두면 색인이 2단이 되어 **에이전트가 「어느 하위를 읽을지」를 또 판단**해야 한다 —
  줄이려던 비용이 다시 는다. **색인은 항상 한 단**으로 둔다.
- **600줄이 넘었다는 건 대개 주제를 굵게 잡았다는 뜻**이다. 안을 열어 보면 서로 다른 상황에서
  읽는 것들이 뭉쳐 있다(실측: 「테스트설계」 안에 **변이 설계 · 구조 함정 · e2e** 가 함께).
  ⇒ 이름을 `<주제>-<하위>` 로 갈라 **평면으로** 늘린다. 색인엔 줄이 하나 더 늘 뿐이다.
- 색인의 **「언제 읽나」가 갈라지지 않으면** 쪼개도 소용없다 — 같은 상황에서 둘 다 읽게 된다.
  쪼개기 전에 **「이 둘은 다른 때 읽는가」**를 먼저 확인하라.

- ☠️ **삭제·이동 전 «제목 단위 대조»로 유실 0건 확인.** 「보관했으니 괜찮다」로 넘기지 마라.
  묶음으로 옮긴 경우 **본체 + 묶음 합산**으로 대조한다.
