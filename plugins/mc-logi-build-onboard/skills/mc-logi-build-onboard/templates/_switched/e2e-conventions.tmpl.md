`{{prefix}}-e2e-author` · `{{prefix}}-e2e-run` · `{{prefix}}-e2e-verify` 는 착수 전 이 파일을 정독한다.
경로·명령·인증·정리 방법의 단일 진실원. **AI 임의 추정 금지** — 여기 없는 값은 사용자에게 묻는다.

```yaml
spec_root:  "{{e2e_root}}"          # spec 파일 위치

api_base:   "{{e2e_api_base}}"      # API 직접 호출용 (fixture·정리에 사용)
run_cmd:    "{{e2e_run_cmd}}"
```

**서비스 기동 — 실행 전 반드시 확인한다(떠 있다고 가정하지 않는다):**
{{e2e_service_up}}

> **재기동할 때는 포트를 잡은 프로세스를 직접 확인해 죽인다**(`lsof -nP -iTCP:<port> -sTCP:LISTEN -t`).
> 이름 패턴(`pkill -f`)으로 죽이면 watch/supervisor 가 띄운 **자식 프로세스가 살아남아 포트를 계속 잡는** 일이 흔하다.
> 그 상태로 재기동하면 새 프로세스가 포트 충돌로 조용히 죽고, **옛 설정이 그대로인 채 "재기동했다"고 착각**하게 된다.
> 기동 후에는 로그나 실제 응답으로 **설정이 반영됐는지 확인**한다(떴다 = 반영됐다가 아니다).

> 이 전제가 깨지면 spec 이 통째로 실패한다. `run` 은 실행 전에 이걸 먼저 확인하고,

## 인증

<!-- IF e2e_auth == none -->
이 앱은 인증이 없다. 시나리오는 곧바로 대상 화면으로 진입한다.
<!-- ENDIF e2e_auth -->
<!-- IF e2e_auth == bypass -->
로그인은 **전제조건**으로만 다룬다 — 다른 것을 검증하기 위해 일단 들어가는 수단이다.

```
{{e2e_auth_bypass}}
```

매 시나리오가 로그인 UI 를 타면 느리고, 로그인 화면이 바뀔 때 무관한 시나리오가 전부 깨진다.
<!-- ENDIF e2e_auth -->
<!-- IF e2e_auth == bypass_and_verify -->
로그인은 **두 역할**을 갖는다. 섞으면 검증 공백이 생긴다 — 반드시 분리한다.

| 역할 | 처리 | 이유 |
|---|---|---|
| **전제조건** (다른 걸 검증하려고 들어감) | 아래 우회 사용 | 매번 UI 를 타면 느리고, 로그인 화면 변경 시 무관한 시나리오가 전부 깨짐 |
| **검증 대상** (로그인 자체가 요구사항) | **화면을 실제로 조작** | 우회하면 로그인은 한 번도 검증되지 않음 |

```
{{e2e_auth_bypass}}
```

> ★ **우회한 시나리오만 있으면 "로그인을 검증했다"고 말할 수 없다.**
> 로그인·인증 흐름을 다루는 UC/AC 가 설계에 있으면 그것을 검증하는 시나리오가 **별도로** 있어야 한다.
> `verify` 는 이 분리가 지켜졌는지 점검한다.
<!-- ENDIF e2e_auth -->

## 셀렉터

<!-- IF e2e_selector == testid -->
이 프로젝트는 `data-testid` 를 쓴다. 우선순위: `getByTestId` → `getByRole` → 텍스트.
<!-- ELSE -->
이 프로젝트에는 `data-testid` 가 없다. 우선순위: **`getByRole`(접근성 이름)** → 텍스트 → CSS.
CSS 구조 셀렉터(`locator("h1")`, `.class`)는 마크업이 바뀌면 조용히 깨지므로 최후 수단이다.
<!-- ENDIF e2e_selector -->

**공통 규칙 — 실제로 돌려보기 전에는 셀렉터가 맞는지 알 수 없다:**
- 부분 매칭 충돌을 경계한다. 한 요소의 이름이 다른 요소의 부분 문자열이면 strict mode 위반이 난다.
  **짝을 이루는 요소에서 자주 터진다** — 상태 표시와 그 상태를 뒤집는 버튼, 입력 필드와 그 확인 필드처럼
  한쪽 이름이 다른 쪽에 포함되는 경우. 상태가 바뀐 뒤에야 드러나므로 첫 실행에서 걸린다.
  → `{ exact: true }` 로 좁히거나, 행·영역 로케이터 안에서 찾는다.
- 목록·표에서는 **행 단위로 좁힌 뒤** 그 안의 요소를 찾는다(`getByRole("row", { name: ... })`).

## 계정

<!-- IF e2e_auth == none -->
인증이 없으므로 계정 개념이 없다.
<!-- ELSE -->
**계정 확보는 setup 프로젝트가 전담한다.** 본 시나리오는 계정이 어디서 왔는지(만들었는지·받았는지)
몰라도 되고, `storageState` 파일만 쓴다. 이 분리가 있어야 가입 시나리오를 건너뛰어도 나머지가 돌아간다.

```
{{e2e_storage_dir}}/<role>.json      ← setup 이 만든 세션 상태 (★ gitignore 필수)
```

### 역할별 계정

{{e2e_roles}}

- 시나리오가 요구하는 역할이 있으면 **그 역할 계정을 setup 에서 확보**한다.
  권한이 없어 403 이 나는 것을 "미커버"로 넘기지 않는다 — 역할을 만들거나 받는 것이 먼저다.
- 역할 부여에 관리자 조작·DB 변경이 필요하면 **되돌리는 방법도 함께 기록**한다.

<!-- IF e2e_account_strategy == self_provision -->
### 조달: 자급자족

계정은 **테스트가 직접 만들고 지운다.** 외부에서 받아오는 자격증명이 없다.
- 가입·승인 등 계정 생성 흐름 자체는 `@provisioning` 시나리오로 **검증 대상**이기도 하다.
- setup 은 그 흐름을 재사용해 역할별 계정을 만들고 `storageState` 를 남긴다.
<!-- ENDIF e2e_account_strategy -->
<!-- IF e2e_account_strategy == seed -->
### 조달: 시드 계정 (사용자 제공)

미리 준비된 계정을 쓴다. **자격증명은 환경변수로 주입받는다.**

{{e2e_seed_accounts}}

- setup 이 이 계정으로 로그인해 `storageState` 를 만든다. 본 시나리오는 여기서부터 시작한다.
- 값이 주입되지 않았으면 **해당 시나리오를 skip 하고 그 사실을 보고**한다(조용히 통과시키지 않는다).
<!-- ENDIF e2e_account_strategy -->
<!-- IF e2e_account_strategy == mixed -->
### 조달: 혼합 — 만들 수 있으면 만들고, 받아야만 하는 것만 받는다

**기본은 자급자족.** 테스트가 계정을 만들고 지운다.
- 가입·승인 흐름 자체는 `@provisioning` 시나리오로 **검증 대상**이기도 하다.
- setup 은 그 흐름을 재사용해 역할별 계정을 만들고 `storageState` 를 남긴다.

**받아야만 하는 경우만 시드를 쓴다.** 새로 만든 빈 계정으로는 검증이 불가능한 시나리오 —
대량 목록·페이징·통계·오래된 이력처럼 **데이터가 쌓여 있어야만 성립**하는 것들.

{{e2e_seed_accounts}}

- 값이 주입되지 않았으면 **해당 시나리오를 skip 하고 그 사실을 보고**한다(조용히 통과시키지 않는다).
- 시드 계정 데이터를 **테스트가 훼손하지 않는다** — 읽기 위주로 쓰고, 쓰기가 필요하면 자급자족 계정으로.
<!-- ENDIF e2e_account_strategy -->

### 자격증명 취급 (예외 없음)

- **spec·규약 파일에 자격증명을 하드코딩하지 않는다.** spec 은 저장소에 커밋된다.
- 환경변수 또는 gitignore 된 파일로 주입하고, 규약에는 **키 이름과 용도만** 적는다.
- 테스트가 스스로 만든 계정의 비밀번호는 시크릿이 아니다(매 실행 새로 만들고 지움).
  다만 그 상수를 **시드 계정에 똑같이 쓰지 않는다** — 둘은 성격이 다르다.
- `{{e2e_storage_dir}}` 는 로그인 세션 그 자체다. **반드시 gitignore.**
<!-- ENDIF e2e_auth -->

## 시나리오 그룹 (선택 실행)

매 실행마다 가입·승인부터 다시 타면 느리다. 태그로 나눠 **필요한 것만 돌린다.**

{{e2e_groups}}

```bash
{{e2e_run_cmd}} --grep @smoke              # 핵심만
{{e2e_run_cmd}} --grep-invert @provisioning # 계정 생성 흐름 건너뛰기
{{e2e_run_cmd}}                             # 전체
```

- 시나리오마다 **태그를 반드시 단다.** 태그 없는 시나리오는 선택 실행에서 누락되거나 항상 딸려온다.
- `@provisioning` 을 건너뛰어도 나머지가 돌아가려면 **계정 확보가 setup 에 분리**돼 있어야 한다(위 계정 절).
- 건너뛴 그룹은 **"검증 안 함"이지 "통과"가 아니다.** 보고에 무엇을 건너뛰었는지 명시한다.

## 테스트 데이터

계정만 데이터가 아니다. **업무 데이터도 시나리오의 전제**다 — 목록·검색·페이징·통계는
데이터가 몇 건 있어야 검증되고, 상태 전이는 특정 상태의 레코드가 있어야 시작된다.
빈 화면에서 "표시됨"만 확인하고 넘어가면 검증한 것이 없다.

| 시나리오 | 필요한 데이터 | 조달 |
|---|---|---|
| 등록·생성 | 없음 (테스트가 만든다) | 자급자족 |
| 목록·검색·페이징 | **여러 건** — 필터가 걸러낼 만큼 | 테스트가 N건 생성, 또는 시드 계정 |
| 상태 전이 | 그 상태의 레코드 | 앞 단계에서 만들어 이어붙임 |
| 통계·대시보드 | 기간에 걸친 누적 | 대개 **시드 계정**(만들기 비현실적) |

<!-- IF e2e_fixture_setup -->
**사전 준비 (fixture):**
{{e2e_fixture_setup}}
<!-- ENDIF e2e_fixture_setup -->

**정리 — 테스트는 자기가 만든 것을 반드시 치운다:**
{{e2e_cleanup}}

- 검증이 **실패해도** 돌도록 `afterEach`/`afterAll` 에 둔다(본문 끝에 두면 실패 시 안 돌아 잔여물이 쌓인다).
- **이전 실행이 남긴 잔여물도 함께** 청소한다(중단·타임아웃으로 정리를 못 한 회차가 반드시 생긴다).
- 식별용 접두사를 정해 그것으로 대상을 특정한다. 고유 이름은 타임스탬프로 만든다(이름·slug 충돌 방지).

## 액터 분리

한 시나리오에 **역할이 다른 사용자가 둘 이상** 나오면(예: 신청자와 승인자) 각각 별도 브라우저 컨텍스트를 쓴다.
한 컨텍스트에서 진행하면 세션 쿠키가 덮어써져 "A 가 한 뒤 B 가 확인한다" 순서가 성립하지 않는다.

## 파일·추적 규약

```
{{e2e_root}}/<시나리오-슬러그>.spec.ts
```

- 파일 상단 주석에 **설계 근거 ID 를 반드시 명시**한다(UC/AC/SCREEN/REQ/NFR).
<!-- IF e2e_design_link == logicraft -->
- LogiCraft `test_scenario`(TEST-NNN)로 등록된 시나리오는 `@design TEST-NNN` 태그를 함께 단다.
  설계 변경 시 `grep "@design"` 으로 영향 spec 을 기계적으로 찾기 위한 앵커다.
- `test.step()` 의 순번은 `test_scenario.steps[].seq` 와 **1:1 로 맞춘다**. 이 대응이 깨지면
  실행 결과를 `record_test_run` 의 `step_results[]` 로 되돌릴 수 없다.
<!-- ENDIF e2e_design_link -->
- 커버하지 못한 AC/UC 는 **파일 하단에 이유와 함께 명시**한다. 조용히 빠뜨리지 않는다.
